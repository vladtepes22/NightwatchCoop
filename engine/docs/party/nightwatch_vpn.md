# Nightwatch VPN: per-install certificates (nwsign)

The Nightwatch VPN is an opt-in OpenVPN network for bbport co-op. Nobody registers; the launcher
enrolls itself once and renews in the background. This document covers the design, the HTTP API, what
the launcher must do, and how to run the service. Code: `tools/vpn/nwsign/`, reference client
`tools/vpn/nwvpn_client.py`, tests `tests/test_nwsign.py`.

The server address is never written in the repo. Below, `<vpn-host>` is the name or address the
launcher ships with.

## How it works

```
launcher                                   VPN host
  | generate EC P-256 key (local, never sent)
  |--- HTTPS 8443 (pinned) POST /v1/enroll {csr} -->  nwsign (user nwsign, sub-CA key)
  |<-- cert (CN = random install id, 7 days), tls-crypt-v2 client key, profile
  |--- UDP 1194 OpenVPN -------------------------->  openvpn: tls-crypt-v2 key + metadata check,
                                                      cert chain root -> nwsign-ca, CRL check
```

- `nwsign-ca` is an EC P-256 sub-CA signed once by the existing root CA. Only the sub-CA key and a copy
  of the tls-crypt-v2 server key live under the service user. The root CA key never leaves root.
- OpenVPN trusts a bundle (root + sub-CA) and loads a CRL bundle (root CRL + sub-CA CRL).
  `verify-client-cert require` is kept.
- Clients are given only the root CA for verifying the server (it signed the server certificate), so a
  stolen sub-CA key cannot be used to impersonate the server. The profile also has
  `remote-cert-tls server`.
- Every install has its own tls-crypt-v2 client key. Its metadata is `"<install id> <expiry unix>"`,
  authenticated by the server key. The `tls-crypt-v2-verify` hook (`nwsign-verify`) rejects expired or
  banned ids before OpenVPN exposes its TLS stack to the packet. `--tls-crypt-v2-max-age` was not used
  because it needs the automatic timestamp metadata, which cannot be combined with our own metadata.
- `duplicate-cn` is removed: one install id equals one concurrent connection (a copied key kicks the
  original instead of being quietly shared).

## Threat model

| Attacker has | Gets | Limit |
|---|---|---|
| The shipped launcher | Can enroll like any user | 3 enrollments / 24 h per IP, 200 / 24 h global |
| One install's key + cert + tls key (stolen file) | One VPN identity | 7 days (+3 day renewal grace if they hold the key), `ban` ends it within minutes; firewall limits clients to port 9307 (party) and ping to each other |
| A packet capture | Nothing useful | tls-crypt-v2 hides the TLS handshake; keys are never sent in clear |
| The enrollment endpoint (flooding) | Nothing | rate limits, 8 KB body cap, 16 threads, 15 s hard request deadline |
| The nwsign host account (service compromise) | Can mint certs and tls keys for any id | Same reach as any client (firewall); rotate the sub-CA (below). Cannot touch the root key. |

What a banned install cannot do: connect (CRL and hook), or renew (403).

Not defended: a user with a valid install can host or join parties like anyone else. The service is not
an identity system; an install id is a random token, not a person.

## Privacy statement

The VPN promises that it logs nothing. nwsign keeps to that:

- Client IP addresses are never written to disk, logs or journal. The HTTP request log and the default
  error handler (which prints the peer address) are disabled.
- Rate limiting is in memory only, keyed by a salted hash of the address (IPv6 by /64); the salt is
  random per process start; entries expire after 24 h. A restart forgets everything.
- Stored per install: install id, certificate serial(s), expiry, banned flag. Nothing else. Installs whose
  certificates expired more than 30 days ago are forgotten (banned ones are kept so the ban holds).
- The certificate subject sent by the client is ignored; the CN is the random install id.

## API (HTTPS, TCP 8443, JSON)

TLS uses a self-signed EC certificate. Clients must pin the SHA-256 of its SubjectPublicKeyInfo (hex;
the installer prints it, `nwsign-admin pin` shows it again). No hostname validation is needed. The
certificate can be replaced without changing the pin as long as the key is kept.

Errors are `{"error": "..."}`. Limits: request body at most 8192 bytes (413), `Content-Length`
required (411), 429 carries `Retry-After` seconds.

### POST /v1/enroll

Request: `{"csr": "<PEM certificate request>"}`. The CSR must be self-signed (proof of possession) and
carry an EC P-256 key. Its subject is ignored.

Response 200:

| field | meaning |
|---|---|
| `install_id` | 32 hex chars, random, generated by the server; also the certificate CN |
| `cert` | client certificate PEM, clientAuth only, valid 7 days |
| `ca_bundle` | PEM of the CA(s) the client must trust for the server (root only) |
| `tls_crypt_v2_client_key` | contents for the `<tls-crypt-v2>` block (secret) |
| `expires` | cert expiry, unix seconds |
| `renew_after` | unix seconds; start renewing once this has passed (default: 4 days after issue) |
| `profile` | `.ovpn` text without any key or certificate block |

To build the final profile append `<ca>`, `<cert>`, `<key>` (the launcher's own private key) and
`<tls-crypt-v2>` blocks to `profile`. `nwvpn_client.py` does exactly this.

Status codes: 400 bad request or CSR, 413, 411, 429, 500.

### POST /v1/renew

Request:

```
{"install_id": "...", "csr": "<PEM, usually a NEW key>", "timestamp": <unix seconds, int>,
 "signature": "<base64 of the DER ECDSA-SHA256 signature>", "cert": "<current cert PEM>"}
```

The signature covers these bytes (UTF-8, `\n` separators, no trailing newline), made with the CURRENT
private key (the one in `cert`):

```
nwsign-renew-v1
<install_id>
<sha256 hex of the csr string exactly as sent>
<timestamp>
```

In openssl terms: `openssl dgst -sha256 -sign client.key < message`. The server checks: cert issued by
the sub-CA, CN equals `install_id`, serial is one it issued, not banned, now is at most 3 days after the
cert expiry, timestamp within 5 minutes of server time, signature valid for the cert's public key. Then
it returns the same body as enroll (same `install_id`, fresh 7 days, new tls-crypt-v2 key, new cert).
The old certificate stays valid until it expires (and is revoked together with the new one on a ban).

This was chosen over mTLS because the pinned HTTPS endpoint then needs no client-certificate
configuration, and the signed message binds the CSR, so a captured request cannot be turned into a
certificate for someone else's key.

Status codes: 401 any authentication failure (including expired beyond grace and "unknown install":
then enroll again), 403 banned, 429 (10 renewals per install per day), 400/413/411.

### GET /v1/health

`{"ok": true}`.

## Launcher integration (what the Nightwatch dev implements)

1. Ship `<vpn-host>`, port 8443 and the SPKI pin (hex) as constants.
2. First use of the VPN option: generate an EC P-256 private key locally (`prime256v1`), build a CSR
   (any subject), `POST /v1/enroll` over HTTPS with the pin check (connect, read the peer certificate,
   hash its SPKI, compare, only then send the body). If your TLS stack cannot pin, use a custom verify
   callback; do not fall back to "trust any".
3. Store the private key at rest protected: on Windows wrap it with DPAPI (`CryptProtectData`, current
   user scope) and keep the ciphertext in the launcher's data folder. Keep `install_id`, `cert`,
   `expires`, `renew_after` next to it (not secret). Never log the key or the tls key.
4. Write the `.ovpn` (profile + ca + cert + key + tls-crypt-v2) to a file only the user can read right
   before starting OpenVPN, and delete it after the connection is up if your OpenVPN launch allows an
   inline config or management-interface push; otherwise keep it user-only.
5. At launcher start (and when the VPN option is on), if `now >= renew_after`, renew: new key + CSR,
   signature made with the old key, then replace key, cert, tls key atomically. If renew returns 401
   ("enroll again") or the grace has passed, enroll again (you get a new id).
6. On 429 wait `Retry-After`; on 403 tell the user the install was blocked; on network failure keep the
   old profile (it works until `expires`).
7. Do not retry enrollment in a loop: three per IP per day is the whole budget.
8. The old shared profile does not work with the new server configuration; remove it.

## Operations

All commands run on the VPN host. The installer puts a wrapper in `/usr/local/sbin`.

```
sudo nwsign-admin stats          # counts only: installs, active, expired, banned, issued/expiring in 24 h
sudo nwsign-admin list           # count, then id + expiry (+ BANNED); nothing about clients' addresses
sudo nwsign-admin ban <id>       # CRL + banned.txt updated at once
sudo nwsign-admin unban <id>
sudo nwsign-admin regen-crl      # also forgets long-expired installs
sudo nwsign-admin pin            # HTTPS pin
```

A ban stops new connections immediately (the hook and the CRL are read per connection). A session that
is already up ends at its next TLS renegotiation (`reneg-sec` default 1 h); to cut it at once, kill the
client through the OpenVPN management interface (127.0.0.1:7505, password in
`/etc/openvpn/server/mgmt.pw`).

The service rewrites the CRL at start and every 6 hours; the CRL is valid 90 days. If `nwsign` is down for
more than 90 days OpenVPN rejects every client ("CRL has expired"): `systemctl start nwsign` fixes it.
The root CRL (`/etc/openvpn/server/crl.pem`, valid until 2041) is copied into the bundle at install time;
if you regenerate it with easy-rsa run `sudo sh install.sh` again (it re-copies it).

Logs: `journalctl -u nwsign` holds only start/stop and internal errors, never client addresses.

### Rotate the sub-CA (key compromise or planned)

```
sudo systemctl stop nwsign
sudo rm /var/lib/nwsign/priv/subca.{key,csr,crt}
sudo sh install.sh              # new sub-CA, new bundle, openvpn restarted
```

Every issued certificate dies at once, so all launchers re-enroll (they fall back to `/v1/enroll`
after a 401/refused connection). Rotate the tls-crypt-v2 server key the same way: delete
`/etc/openvpn/server/tls-crypt-v2.key` and `/var/lib/nwsign/priv/tc2-server.key`, run install.sh.

### Install and rollback

See `tools/vpn/nwsign/install.sh` (idempotent) and `uninstall.sh [--purge]`. Install changes
`server.conf` (backup `server.conf.pre-nwsign`), adds `ca-bundle.crt`, one iptables line for 8443/tcp in
`add-openvpn-rules.sh` / `rm-openvpn-rules.sh` (backups `*.pre-nwsign`) and a systemd unit. The installer
restores the old `server.conf` by itself if OpenVPN fails to start.

Tunables are in `/etc/nwsign/nwsign.json` (`enroll_per_ip_day`, `enroll_global_day`, `cert_days`,
`renew_after_days`, `grace_days`, ...; defaults in `nwsign_core.DEFAULTS`). Restart the service after a change.

## Game lobby (nwlobby, UDP 9310)

LAN discovery (UDP 9308 broadcast) does not cross an OpenVPN tun, so VPN players would not see each
other's games. `tools/vpn/lobby/nwlobby.py` is a tiny in-memory lobby on the VPN server's tunnel address
(`10.8.0.1:9310`, reachable only from the tunnel). Code: `tools/vpn/lobby/`, game side
`gpu/shim/net/party_vpnlobby.*`, launcher side `lobby_*` in `launcher.py`, tests `tests/test_nwlobby.py`,
`tests/test_launcher_vpnlobby.py`, `test_vpnlobby()` in `tests/test_party_net.cpp`.

Off by default: the setting `party_vpn_lobby` (bbport.ini; launcher checkbox *Nightwatch VPN lobby*; in the
game *System > Party network > Nightwatch VPN lobby*, host's row; env `BB_PARTY_VPN_LOBBY`).

### How a join works

```
host game (10.8.0.x)                 lobby 10.8.0.1:9310                guest launcher (10.8.0.y)
  announce every 10 s ------------->  entry per source address
  (name, port, slots, build,          expires after 30 s          <---- list request (page offset)
   password flag)                                                  ----> names, flags, slots, build,
                                                                         host tunnel address + port
                                                                  guest picks a game, types the password,
                                                                  the game joins <address>:<port> + password
```

Joining a plain `host:port` needs the host's password, or an open party. A listed host without a password
is an open party for the tunnel's subnet (`party_open_rules.h`; `party_open` extends it to the host's LAN
and other VPN subnets), and its row has an open lock (a password: a closed lock). Anyone on that network can join and holds the same link
key, so the link's encryption does not protect an open party from them. With a password the guest types
the password the host told them; the launcher starts the game as a guest with `BB_PARTY_CODE=<tunnel address>:<port>` and
`BB_PARTY_PASSWORD`. The VPN firewall already lets clients reach each other's party port 9307 (UDP and
TCP) only.

### Wire format (version 1, big endian)

Every packet starts `0xfa 'L' 0x01 type`. At most 512 bytes in (longer datagrams are dropped unread), at
most 1024 bytes out. Nothing malformed is ever answered.

| type | name | body |
|---|---|---|
| 1 | announce (host to lobby) | flags u8 (bit 0 password), port u16, players u8, max u8, build: u8 len + printable ASCII (at most 32), name: u8 len + UTF-8 (1 to 48 bytes) |
| 2 | list (guest to lobby) | offset u16: the first entry wanted in the sorted list |
| 3 | reply (lobby to guest) | total u16, offset u16, count u8, then count entries: ipv4 (4), port u16, flags u8 (bit 0 password, bit 1 this is your own entry), players u8, max u8, name (u8 len + UTF-8), build (u8 len + ASCII) |
| 4 | bye (host to lobby) | none: removes the sender's entry |

A reply holds at most 16 entries and 1024 bytes; the client asks the next page with `offset += count`
until `offset >= total`. Entries are sorted by name (case-folded), then address. Reference encoder and
parser: `nwlobby.py` (`encode_announce`, `encode_list`, `parse_reply`). The same announce bytes come out of
the game's C++ encoder (`fa4c010101245b01040b302e372e3720286162632905416c696365` for *Alice*, port 9307,
1/4 players, build `0.7.7 (abc)`, password): both tests check this vector.

### Rules the lobby enforces

- Only senders from `10.8.0.0/24` are answered; the network, broadcast and server (`.1`) addresses and
  everything else are dropped without a trace (no state is created for strangers).
- One entry per source address (a new announce replaces the old one), at most 300 entries, 30 s to live.
  Entry address = the datagram's source: OpenVPN drops packets whose source is not the client's own tunnel
  address, so a host cannot list someone else's address, and the entry never carries an address field.
- Rate limit per source: a bucket of 8 packets refilling 2 per second (announce, list and bye alike).
- Name: UTF-8, control, format (bidi, zero width), separator and private-use characters and combining marks
  stripped, spaces folded, at most 16 characters; an empty or non-UTF-8 name is refused. The build is
  printable ASCII at most 32 bytes. Port 1024 or higher, 1 to 8 slots, players not above slots.
- Replies are capped (16 entries, 1024 bytes) and paginated, so one query cannot be used to amplify.

### What the player sees (and never sees)

The list shows the **character name** of the host (the name in the host's save, read from the game, not an
account, Discord or Steam name), slots, password flag and version. The tunnel address is kept in memory by
the launcher for the join only: it is not shown, not copied, not saved in `launcher_settings.json` and not
written to logs. A game with a different version is greyed out; your own game is left out of your list.

### Privacy

Nothing is written to disk and nothing is logged: the service prints nothing and has no state directory
(`DynamicUser`, `ProtectSystem=strict`, no `ReadWritePaths`; the unit sends stdout to null). The list lives in
process memory and is gone at a restart. The game's own log says only that it announces (no address).
A VPN player can read the tunnel addresses of the hosts in the replies (the launcher hides them from the
UI); all of them are already reachable to each other on port 9307 by the firewall design.

### Operations

Install (root, from a copy of the directory; idempotent):

```
git archive HEAD tools/vpn/lobby | ssh visy@<vpn-host> 'tar xf - -C ~'
ssh visy@<vpn-host>
sudo sh ~/tools/vpn/lobby/install.sh
```

The installer copies the script to `/opt/nwlobby`, installs and starts `nwlobby.service`
(`After=openvpn-server@server`; `10.8.0.1` exists only while OpenVPN runs, so the script also retries the
bind), and opens UDP 9310 from the tunnel in both firewalls: the iptables-nft rules (the Nightwatch
`add-openvpn-rules.sh` already has the lobby rule in `NW_VPN_IN`; the installer only adds a rule, to the
script and live, when it is missing) and the nftables `inet filter` table (live
`nft add rule inet filter input iifname "tun0" udp dport 9310 accept` and the line after `udp dport 1194
accept` in `/etc/nftables.conf`, checked with `nft -c -f`, backup `*.pre-nwlobby`). `uninstall.sh` reverses
all of it. The unit is hardened (`DynamicUser`, `NoNewPrivileges`, `ProtectSystem=strict`,
`RestrictAddressFamilies=AF_INET`, empty capability set, syscall filter, `IPAddressDeny=any` except the
tunnel network, 64 MB). Check: `systemctl status nwlobby`; there are no logs to read by design.

**Counts socket** (2026-10-31): nwlobby also answers a stats request (type 5) on `127.0.0.1:9311`, loopback
only (never the tunnel; `NWLOBBY_STATS=off` disables): JSON counts of listed games, players in them, public
(no password), full, public with room, free slots, party sizes and the top 5 versions. No names or addresses.
`~/nwvpn/vpn_count.py` (the Iosefka forced command) adds them to its reply as `lobby`; Iosefka stores them with
each 5-minute sample and shows them in `/vpnstatus`, `iosefka vpn-status` and the daily report (24 h averages
and peaks). `install.sh` adds `iifname "lo" udp dport 9311 accept` to nftables (input policy drop).

**No status file**: Debian's `openvpn-server@.service` passes `--status /run/openvpn-server/status-%i.log`
itself, so removing the status line from server.conf was not enough: a RAM status file with every client's real
address existed (found 2026-10-31). `tools/vpn/server/no-status-file.sh` (root) adds a systemd drop-in with the
same ExecStart minus `--status`; `--undo` removes it.

Test override (never set in production): `NWLOBBY_BIND=127.0.0.1:19310 NWLOBBY_NET=127.0.0.0/8 python3
nwlobby.py` serves on loopback and accepts loopback senders. The game and launcher use the matching
`BB_PARTY_VPNLOBBY_ADDR=127.0.0.1:19310` (sends from 127.0.0.1 and skips the 10.8.0.x address check);
`BB_PARTY_VPNLOBBY_NAME` replaces the character name in the game (synthetic name for tests).

### What the launcher must do (the Nightwatch launcher)

1. Show *Nightwatch VPN lobby* as an opt-in checkbox next to the VPN option; write bbport.ini
   `party_vpn_lobby=1/0` (the game reads it live; the same checkbox exists in the game's System menu).
2. When on and the VPN adapter has a `10.8.0.2`-`10.8.0.254` address: every 5 s send a list request from
   that address to `10.8.0.1:9310` (page through the replies), 1 s timeout, strict parser (`lobby_parse_reply`
   in `launcher.py` is a model). Do not send when the VPN is off.
3. Show the list: name, slots, password flag, version (grey out another version). Drop entries flagged
   *own*. Never display, copy or log the address.
4. *Join*: ask for the password, then start the game as a guest with `BB_PARTY=join`,
   `BB_PARTY_CODE=<address>:<port>` and `BB_PARTY_PASSWORD=<password>`; keep the address out of saved settings.

## Tests

`python -m unittest tests.test_nwsign` needs the `openssl` CLI (Git for Windows' is fine). Tests that need
the real `openvpn` binary are skipped when it is absent. `tools/vpn/nwvpn_client.py` is the reference for
the wire format. The lobby: `python -m unittest tests.test_nwlobby tests.test_launcher_vpnlobby` and
`party-net-test` (`ninja -C out/gpu party-net-test`).
